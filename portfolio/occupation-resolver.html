The occupation resolver

Any messy employer job title, resolved to a federal occupation code and a recruiter-legible canonical name, with certainty spent cheapest first and the unmatched flagged, never guessed.

Machine learning · LLM systems · information retrieval · data engineering. In production on employer HRIS panels and public postings, under tenant isolation.
01

The problem

Employers name the same job a hundred ways: "AmbFloat LPN / II", "RN/Care Manager", "Sr. Scrum Master (Remote, LOCALS)". Nothing downstream works, no benchmark, no forecast, no career transition, until those titles collapse onto one federal spine. And there is no ground truth to check against: no labelled set says which code is correct. Getting this stage right, cheaply and reliably, is what makes everything after it possible.

02

How it works

01One job, a hundred names

Raw titles carry shift tags, unit codes, seniority markers, and location suffixes, all noise before anything can be judged. The first move strips and normalises the input so what remains is the job, not the paperwork around it.

Information retrieval · data engineering

02Spend certainty cheaply

A ten-stage cascade resolves what it can at each step and passes only the residual on: exact caches and keyword rules first, then substring and embedding matches, then the models. Each stage has a confidence floor, and nothing passes below its floor.

Information retrieval · data engineering

03Three models, called in sequence

An open-source embedding baseline handles the well-behaved majority for free. A fine-tuned in-domain encoder carries the ambiguous middle. A local, tenant-isolated LLM adjudicates the long tail, novel titles, marketing-speak, compound roles, with JSON-constrained output.

Machine learning · LLM systems

04Labels without a labelled set

With no gold standard to train on, labels are generated by a locally-run LLM over normalised employer extracts, then reviewed, turning an unlabelled problem into a supervised one at scale. That corpus is what the in-domain encoder learns from.

Classification beats retrieval
On the hard set, a classifier reached 45.5% top-3 against a 40.4% ceiling for oracle retrieval. Retrieval is corpus-bound. No better index could close the gap.
More capacity hurt
At roughly 17k training examples, a frozen-encoder probe (45.5%) beat LoRA (42.4%) beat full fine-tuning (32.3%), monotonically. Data, not parameters, was the remaining lever, so the architecture keeps the encoder frozen and spends effort on labels.
Layers are evaluated where they run: the classifier on the full stream, the encoder only on the residual that reaches it.
03

Final state

The resolver above matches against a small synthetic sample. In production the same input runs the three model layers with the ten-stage cascade in front, over employer HRIS panels and public postings, with inference kept under tenant isolation. The evaluation numbers are from real held-out runs. Every code a title becomes is traceable to the stage that produced it, and titles with no confident match are flagged for review rather than forced.
